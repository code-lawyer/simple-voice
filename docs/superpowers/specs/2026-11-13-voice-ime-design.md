# 本地语音输入法：产品与开发设计

日期：2026-11-13  
状态：语音部分仍有效。产品范围已被 `2026-11-13-pinyin-voice-ime-design.md` 取代：现在要做全拼整句加语音。与新文档冲突时以新文档为准。  
这份文档同时是产品需求（PRD）和第一版的开发基线。实现计划在你认可全文之后再拆。

## 要做什么

做一个 Windows 上的开源语音输入法。识别、词库、音频都在本机。产品行为以这台电脑上的微信输入法（WeType 3.0.1.35）为参照：它是系统输入法，快捷键开麦，字先出现在光标旁，确认后上屏，用过的词留在本机词库里，下次更容易打出来。

我们不接腾讯的语音服务，不使用、不附带它的程序和模型。

## 为什么这样定

微信输入法的语音在用的时候把音频上传到腾讯，官方隐私说明写明用完不在服务器留存；安装目录里也没有一份可独立使用的大语音模型。本机真正留下来的是词库：上屏过的词进个人词典，常用语另算，默认不上传。

这个项目要的是同一套手感，加上一条他们没有默认给 Windows 语音的保证：音频不出这台电脑。

## 目标

- 在任意使用 Windows 输入法的文本框里，用语音把字输进去。
- 字先出现在光标旁边的框里，按回车才进入文档。
- 说错了可以整段作废，重说。
- 你确认上屏过的习惯词句自动留下，以后同样的读音优先用你的写法。
- 默认可离线使用。

## 非目标

第一版不做这些：

- 拼音、笔画、五笔键盘，以及候选条选词。
- 在确认框里改字。
- 把整句录音当成下次识别的模板。
- 手动维护常用语、细胞词库、跨设备同步。
- 云端识别、翻译、问 AI、录音笔整理。
- 英文为主、粤语、方言。中英夹杂能出多少算多少，不为此换模型。
- Linux、macOS、Android。
- 把微信输入法、Feelime、VocoType 的代码或模型拿来改。

## 做成了仍算失败

- 音频或词库在用户没有明确打开同步时离开本机。
- 确认之前，文档里已经出现这段字。
- 清空重说的那一遍被写进词库。
- 只上过一次屏的普通句子，把下一次正常识别整个带偏。
- 必须安装微信输入法，或必须能访问腾讯服务器。

## 你已经定下来的用法

这些是你的决定，不是实现时的默认猜测。

1. 运行在 Windows。把它选成当前输入法之后，光标在哪个文本框，就可以在哪个文本框输入。
2. 只有语音，没有拼音键盘。
3. 确认框贴着光标。换文本框，框跟着走。
4. 说话时字在框里跟着声音长，此时文档里没有这段字。
5. 这段说完，你看框里的字。没错按回车，字落到光标处。
6. 框里整段不对：清空，再重新说。不在框里改，也不挑候选。
7. 麦由快捷键打开，快捷键可以改。按一次就开始，说话时不用按着。
8. 习惯词句在你确认上屏之后自动攒下。不做成一张要自己添加的词表。
9. 对照微信输入法的语音输入和词库记忆来做，识别换成开源本地模型。

## 从微信输入法观察到的事实

观察范围是 `C:\Program Files\Tencent\WeType\3.0.1.35`、本机数据目录的文件名和结构，以及微信输入法公开的隐私说明。没有读取个人词条的内容。

- 它是 TSF 输入法，界面进程和引擎进程分开。重模型不该塞进每一个目标程序。
- 语音界面有录音中、上屏、删除、记录。程序文案写着快捷键启动语音，以及实时转写。
- 安装包自带 16 kHz 离线静音检测：一段最长约 60 秒，停顿大约 300 毫秒量级就收束。
- 语音识别依赖网络。程序里有「网络异常，语音中断」。隐私说明写的是使用期间上传语音、服务器不留存。
- 个人词典在本机 LevelDB（`DictDir2\v5`）。另有用户热词库。上屏会把词写回用户词库，引擎按音节查找。这是拼音输入法的记词方式。
- 常用语是另一套，可以自己保存文字。隐私说明把「重复多次的输入」和「主动导入」都算本地记忆。
- 个人词典和常用语默认不上传。跨设备同步是另外打开的功能。

我们采纳的是：系统输入法、快捷键、光标旁确认、上屏后记词、词库留在本机。我们不采纳的是：上传音频、拼音选词、必须联网。

## 一轮输入

1. 用户用系统的输入法切换，把本输入法设为当前输入法。光标放在要写的位置。
2. 按一次语音快捷键。麦打开。光标旁出现框，状态是「正在听」。
3. 用户说话，手离开快捷键。框里的字随着流式识别变长。文档不变。
4. 用户停口。静音检测判定这段结束，麦关掉。定稿模型和标点模型跑完后，框里换成带标点的定稿，状态变为「待确认」。
5. 回车：把框里的定稿插入光标处，等待应用确认写入成功后框消失，词库按下面的规则记一笔。
6. 待确认时按 Esc：框消失，这段不进文档，也不进词库。下一遍需要再按快捷键。
7. 正在听的时候再按一次语音快捷键或按 Enter：提前结束录音，不等静音；先显示「正在校准文字」，校准完成后进入「待确认」，再次 Enter 才写入。校准中按 Enter 不预约写入。
8. 待确认时再按语音快捷键：丢弃当前这框，马上再听。

密码框、没有文本插入位置、本输入法不是当前输入法时，快捷键不做任何事。

2026-11-15 稳定性补充：等待应用确认时显示“正在写入正文”，暂不接受重复回车、Esc 或重新录音。5 秒没有确认、或连接断开时保留原文，提示先核对正文；只有确认未写入后才由用户按回车重试。未识别到文字时不提供写入动作。词库故障不影响已经写入的正文，也不重放写入。

2026-11-15 预览确认补充（用户已确认）：自动停口与手动停录都必须先在浮层显示最终文本。保留已有本地定稿、标点与词库校正能力；不增加云端润色、R2T2 或改变原意的补写。只有在待确认状态下明确按 Enter，才写入当前显示的最终文字。

## 词库怎么自动记

微信输入法能记住「你选中的那一个词」，是因为拼音上屏时词是分开选的。语音一次上屏的是整句，没有这一下选择。所以记词规则要另写，不能照搬它的音节用户词库。

上屏之后：

- 用本地分词把定稿拆开。
- 2 到 8 个字的词写入本机词库，使用次数加 1。单字不记。
- 超过 8 个字的整句第一次上屏先保存在本地“待学习”记录，不参与识别偏好。同一句在保存期限内再次原样上屏，才作为一条词条记下。这样满足「习惯词句会留下」，也满足「确认过一次的整句不要把下次识别整个带偏」。
- 次数为 1 的词只保存，不改变识别结果。同一个词第二次被上屏之后，才开始在同音竞争里优先使用它。
- 清空、识别失败、未按回车，都不写词库。
- 超过 180 天没有再次上屏的词，不再参与优先。超过 365 天删掉。
- 2026-11-15 用户确认：首次长句的“待学习”记录也按 365 天未再上屏删除。历史记录没有日期，首次启动新版时按升级当天补齐一次，后续启动不重新计时。清理在启动及下次识别/记词时执行。
- 不保存音频。词库里是文字、拼音、次数和最后上屏时间。

识别时怎么用：

- 定稿出来之后，按拼音把识别结果里的同音词换成用户词库里次数更高、且次数至少为 2 的写法。
- 例：词库里「张杉」已经有 2 次，这次定稿是「张山」，拼音相同，框里给用户看的是「张杉」。
- 读音本身就认错了、拼音对不上的词，词库换不回来。第一版接受这个限制，不用重训模型来补。
- 词库变化后，在下一句开始前重新加载替换规则。一句正在识别时不改规则。

托盘菜单里有「最近记住的词」。可以删除一条。删除立即生效于下一句。第一版没有导入、导出和云同步。

## 实现时由我定的选择

下面这些你没有口头指定。写在这里是为了能直接开工，你看文档时可以改。

| 事项 | 决定 |
| --- | --- |
| 语言和构建 | C++17，CMake，MSVC。不引入 Flutter，不引入 .NET。 |
| 进程 | 一个常驻引擎进程加载模型。TSF 文本服务只负责焦点、光标位置、按键和插字，经命名管道和引擎通信。 |
| 确认框 | 独立的小窗口，用 TSF 的光标矩形定位。不把未确认文字写进目标程序的组合字符串。 |
| 默认识别 | 流式草稿：`sherpa-onnx-streaming-zipformer-ctc-zh-int8-2025-06-30`。定稿：`sherpa-onnx-zipformer-ctc-zh-int8-2025-07-03`。运行时用 sherpa-onnx。 |
| 标点 | 定稿后接 `sherpa-onnx-punct-ct-transformer-zh-en-vocab272727-2024-04-12-int8`。用户确认的是加过标点的文本。 |
| 不用的模型 | 默认不加载 SenseVoice、Paraformer、Whisper、Qwen、FireRed。它们不是第一版的识别引擎。 |
| 词库文件 | SQLite，放在当前用户的本地应用数据目录。拼音用分词器自带的读音。替换规则用 sherpa-onnx 的中文同音词替换，规则文件随词库重建。 |
| 分词 | cppjieba。用户词次数达到 2 后加入分词词典，让这个词下次能被当成一个词。 |
| 快捷键默认值 | Ctrl+Alt+Space。设置窗口里录制新组合。冲突或系统保留键就拒绝并保持原键。 |
| 清空键 | Esc。 |
| 音频 | 16 kHz、单声道、16 bit。只在内存里。一段最长 60 秒，到点强制进入待确认。静音约 500 毫秒判定说完。 |
| 回车碰到定稿还没算完 | 等定稿和标点结束再插入，不插入流式草稿。 |
| 许可证 | 本仓库代码用 Apache-2.0。不链接 GPL 输入法。模型权重另按各自模型卡的许可随安装包分发，发布前核对，不把权重许可写成 Apache。 |
| 运行环境 | 仅 CPU。建议 8 GB 内存、4 个逻辑处理器。4 GB 不作为支持配置。不要求独立显卡。 |

模型取舍的原因：用户以中文为主，2025 年的中文 Zipformer CTC 在普通话测试集上优于先前考虑的 2023 双语流式模型和 SenseVoice 定稿。CTC 没有 sherpa-onnx 的解码期热词接口，所以习惯词放在定稿之后的同音替换里做。这是用「中文更准」换「词库不能在解码束里改分数」。

流式模型公开样例大约是 1 个线程、5.6 秒音频、实时率 0.14。定稿 int8 的公开字错率是 AISHELL 测试集 1.74%，WenetSpeech test_net 5.92%，test_meeting 7.75%。流式那一档在 icefall 表上的 AISHELL-1 测试集 1.97% 来自 PyTorch 贪心解码，不是这份 int8 文件本身。两套数字不能并成一张总表。

## 架构

```
目标程序
  └─ TSF 文本服务（轻）
        │  焦点、光标矩形、快捷键是否该响应、回车/Esc、插入文字
        ▼
命名管道
        ▼
引擎进程（重，全局一个）
  ├─ 麦克风采集
  ├─ 静音检测
  ├─ 流式识别 → 草稿
  ├─ 定稿识别
  ├─ 标点
  ├─ 用户词库与同音替换
  └─ 模型常驻
```

托盘图标属于引擎进程。设置窗口只改快捷键和查看、删除最近的词。

管道消息保持很少几种：开始听、音频块或由引擎自己采音、草稿、定稿、上屏结果已记词、取消、配置变更。采音放在引擎进程里，文本服务不碰麦克风。这样换焦点时录音不会跟着目标进程一起死掉。

插入文字使用 TSF 的当前选区插入。不模拟键盘，不用剪贴板。目标程序因此走正常的撤销和输入事件。

## 数据

SQLite 表 `entries`：

| 列 | 含义 |
| --- | --- |
| text | 词或后来重复过的短句，唯一 |
| pinyin | 空格分隔的音节，用于同音比较 |
| count | 上屏次数 |
| last_commit_unix | 最后一次上屏 |
| kind | `word` 或 `phrase` |

配置放在旁边的 JSON 里：快捷键、是否开机启动。第一版开机不自启，引擎随输入法第一次激活而启动，用户退出托盘后下次激活再拉起。

## 第一版验收

在记事本、Edge 地址栏以外的网页文本框、以及一个 Win32 编辑框里，手动完成这些步骤：

1. 切换到本输入法，光标在正文，按默认快捷键，说话，框出现在光标旁，正文不变。
2. 停口后框里变成带标点的句子。按回车，正文只增加这一句，框消失。
3. 再说一段，按 Esc，正文不变。检查词库，这次没有新次数。
4. 把同一个 2 到 8 字的词用语音上屏两次，第三次说成常见同音错词时，待确认框里是用户的写法。
5. 只上屏一次的整句，下次说别的内容时，结果不被那句整段替换。
6. 拔掉网络后，上述识别仍然完成。
7. 进程目录和用户数据目录里不产生这段音频的文件。

自动化测试先覆盖：分词记词、次数从 1 到 2 才开始替换、同音才替换、过期不替换、Esc 不写库。TSF 和真实麦克风不做单元测试。

## 建议的实现顺序

1. 文本服务能在记事本的光标处插入固定字符串，框先用假文本。
2. 接上回车、Esc、快捷键和「待确认」状态。
3. 引擎进程、采音、静音检测、60 秒上限。
4. 流式草稿和定稿、标点。
5. SQLite 记词和同音替换。
6. 托盘里的快捷键设置和删词。

每一步都能在记事本里看出对错，再做下一步。

## 已知限制

- 同音替换救不了读音被认成另一个词的情况。
- 替换规则不能在一句进行中热更新。
- 部分全屏或自绘程序拿不到可靠的光标矩形。拿不到时，框改放到该窗口客户区右下角，仍然不把未确认文字写入文档。
- 模型文件大约是流式 155 MB 加定稿 350 MB，再加上标点和分词词典。内存占用以实机为准，发布说明里写测量值，不把手机上 SenseVoice 的内存数字挪过来。
